Identity, keys, and DOM reuse

Predict whether React preserves or resets by asking one question: is this the same identity?

Identity rule

For state preservation, React matches a rendered thing by type, position in the parent, and, when present, key.

Change State DOM node Effects
Same type, same position, same key Preserved Usually reused Updated if dependencies changed
Different key in same position Reset Replaced Old cleanup, new setup
Different type in same position Reset Replaced Old cleanup, new setup
Index key after reorder May attach to wrong item May reuse wrong row Follows mistaken identity

Two uses of key

  1. Give list items a stable identity across reorder, insert, and delete.
  2. Force reset of one subtree when you want a fresh state and fresh DOM.

Ref consequence

Refs follow the committed DOM node. If a subtree remounts because type or key changed, the old ref becomes null during cleanup and then points at a new node after commit.

Smell check

  • If a user's typed input jumps to another row after reorder, suspect index keys.
  • If a form unexpectedly clears, suspect a changed key or changed position.
  • If a widget instance leaks, suspect missing cleanup on remount.
