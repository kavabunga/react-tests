Lesson 7 · Identity and reuse · 30 minutes

Identity, keys, and DOM ownership

The hard question is not “did React re-render?” It is “did React treat this as the same thing?”

← Lesson 6: Hooks across render, commit, and paint

Tangible win Predict whether a state value, DOM node, ref, or Effect will survive the next render.

1. The identity rule

React preserves state by identity, not by source code text. The practical rule is:

same type + same position + same key
= same identity

When identity stays the same, React tries to reuse the existing subtree: state is preserved, DOM nodes are often reused, refs keep pointing at the same committed nodes, and Effects only restart if their dependencies changed.

When identity changes, React remounts: old cleanup runs, old DOM nodes are removed, refs detach, new DOM nodes are committed, and state starts fresh.

2. Props do not define identity

If the same component type stays in the same position, changing props alone does not reset its state. 

{isTaylor
  ? <Counter person="Taylor" />
  : <Counter person="Sarah" />}

Without explicit keys, both branches produce one Counter in one position, so React keeps the same state. The person label changes, but the local counter state survives.

3. What key really changes

key is not a render hint. It is an identity override inside one parent.

{isTaylor
  ? <Counter key="Taylor" person="Taylor" />
  : <Counter key="Sarah" person="Sarah" />}

Now React sees two different identities in the same position. Switching players remounts the subtree: local state resets, the old ref detaches, and Effects clean up and set up again.

A changed key is a controlled reset. Good for clearing a form. Bad when it happens by accident.

4. DOM ownership follows identity

You already learned that React owns DOM nodes inside a root. The missing piece is that React only keeps owning the same node while identity stays the same.

  • Same identity: React may update attributes and text on the existing node.
  • New identity: React removes the old node and commits a new one.
  • Refs follow the committed node, so a remount means a new ref.current.

This is why a keyed reset can clear uncontrolled input state and why a keyed canvas can lose its drawing: the DOM node itself changed.

5. Stable keys in lists

In lists, key tells React which logical item each child represents across reorder, insert, and delete. A stable data id preserves the right identity. 

items.map((item) => (
  <Row key={item.id} item={item} />
))

Index keys work only when the list order never changes and items are never inserted or removed in the middle. If order changes, React can preserve the wrong state on the wrong row because it matched by position, not by item identity.

Primary source: Rendering Lists.

Stable key

key={item.id}

Local state, focus, and refs stay attached to the same logical item.

Index key

key={index}

Local state can move to another row after reorder because identity followed position.

6. Re-render vs remount

Question Re-render, same identity Remount, new identity
Local state Preserved Reset
DOM node Usually reused Replaced
Ref Same node if reused Old ref detaches, new ref attaches
Effect Only restarts if dependencies changed Old cleanup, new setup
