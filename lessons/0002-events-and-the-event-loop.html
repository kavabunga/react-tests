Events and the event loop

A click is not “React running.” It is a browser task. React’s onClick is a listener inside that task.

Tangible win Predict the log order of a click, a microtask, a timeout, and a paint-related callback.

From Lesson 1, one missing sentence

You already have HTML and DOM. The third piece is paint: the browser turns the live DOM and CSS into pixels. A node change does not paint by itself. Paint is a later step on the event loop.

DOM nodes receive events

Elements implement EventTarget. addEventListener stores a function on that object. When the user clicks, the browser creates an Event and runs matching listeners as JavaScript. 

const button = document.querySelector("button");

button.addEventListener("click", (event) => {
  event.target === button;
  true
});

React’s onClick={handler} is the same idea: React registers a listener and later calls your function. See Responding to events.

One loop, three slots

1 · Task One JS job

A click, a script, or a setTimeout callback. JavaScript runs this to the end.

2 · Microtasks Drain the queue

queueMicrotask and Promise then run now, before paint.

3 · Paint Maybe update pixels

Then the browser may layout and paint, then take the next task.

MDN states this order: one task, then all waiting microtasks, then the browser may update rendering. Using microtasks.

What this changes in React

      

        When you click a React button, that click is one task. Your handler runs in that task. If
        the handler calls setState, React can do more work before the browser paints. A
        setTimeout(..., 0) handler is a later task, after paint may already have
        happened.
      

      

        You do not need the React details yet. Hold this rule:
        user events, React work, and paint share one thread and one loop.
